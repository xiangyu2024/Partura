  第 1 次自检没过(停在自检这步,没算 §A~§D),诊断出书①的 universe 构造错把 D30 的可得性也算了进去,
  修正后第 2 次自检四项全过,跑完 §A/§B/§C/§D。两次都 exit 0,**都计入服务器运行次数**。
- `g_tail` 的算子换了:工单写的 `cs_quantile_q75` 经 `study.sh src` 核实后,语义是"标记当天最高的 75%"
  (`x >= 当日 25 分位`),不是"标记最高 25%";真正给出"最高 25%"标记的是 `cs_quantile_q25`。已换成 `cs_quantile_q25`,
  意图("罚 D30 最高一档")没变,只是工单文本把算子名记错了。详细源码摘录见 `07_S2_overlay.md`。
- 事实部分已补进 `notes/F108_max_ntkurt_close/07_S2_overlay.md`、`07x_3_x3_attrib.md`(两个新文件);
  `解读`一节留空,没有写。

  `runs/.../S2_overlay.json` 的 `books.sweep` 只扫 train,`by_rank.splits.valid` 只存了 hl3 那一行,JSON 里没有
  valid@hl0。没有拿自选半衰期的数冒充,照实空着(详见下文 2.2)。`k_mean30` 的 `by_year` 诊断表也没产出
  (工具行为:`by_year`/`neutralise`/`profile` 只对**本次 run 的 stage 内变体**算,不像 `rank_corr` 会跨阶段读缓存;
  这个并排表改由 `x3_attrib` §C 的 book①给出,数值上 book①≈`k_mean30`)。
- **运行预算**:本研究累计服务器运行(含 S0,按 state.md 既定口径)= S0 + x1_anatomy + x2_longonly + S1_nodes +
  S2_overlay + x3_attrib×2 = **7 / 8**,只剩 **1 次,留给 final,零余量**。R2 原计划 2 次,实际用了 3 次
  (多出的 1 次是 x3_attrib 的自检失败重跑)。

### 2.5 `g_tail` 最后用的表达式 + `cs_quantile_q75` 语义

最终表达式:`sub(cs_rank(cross_mean(day_std(Amt), 30)), mul(cs_quantile_q25(cross_mean(day_max(pow_1_5(pow_2(nt_ts_kurt(Close, 30)))), 30)), 0.25))`。
`cs_quantile_q75(x)` 的内核语义(`nd_cs.cs_quantile`,源码见 `07_S2_overlay.md`):参数就是"标记当天最高的那个比例",
`q75` 标记**最高 75%**(等价 `x >= 当日 25 分位`),**不是** "x 高于 75 分位"。标记"最高 25%"(`x >= 当日 75 分位`)
的是 `cs_quantile_q25`,已换用,未走权重退路。

## 3. 没人要但值得注意的(异常与意外)

1. **x3_attrib 第 1 次提交的自检失败,是执行自己的实现 bug,不是工具或数据的问题**——已在"做了什么"里详细交代,
   诊断和修正过程也写进了 journal 第 18 条。这把 R2 的服务器运行从计划的 2 次变成 3 次,把全研究运行预算从
   state.md 预留的"2 次(1 次 final + 1 次余量)"直接吃到只剩 final 这 1 次、**零余量**——R3 不能再加任何实验
   (哪怕是最便宜的 `exec`),必须直接裁决 + 读留出段。
2. **H18(单点权重 vs 平台)不是一个干净的二选一**:相对家族基准(+12.6%/+22.3%),w∈[0.1,0.6] 在两段都明显更好,
   不是"只有 0.25 一档赢"的尖峰;但在 train 上 0.25 这一点本身比它的近邻(0.15/0.4)高出将近 1pp,不是完全平的
   平台。两种描述("有一定宽度的隆起,顶点在 0.25" vs "尖峰")都不完全贴切,具体数字见 2.6/§D,留给主研定性。
3. **H17 的三个安慰剂里,`p_k2`(混入家族自己的第二个成员 K2)最接近复刻 g_w25**(train +14.1% 只差 1.0pp,
   但 valid +22.1% 已经**低于**家族基准 +22.3%,即 valid 侧增量是负的)——`p_ivol`/`p_cap` 两段都明显更差、
   train 还跌破家族线。按工单"任一安慰剂增量≥g_w25增量→H11否定"的判据,三者都没达到,但 `p_k2` 这一条值得主研
   专门看一眼(它不是一个"随便什么都行"的信号,而是家族内部另一个已知算子,这本身可能是另一种需要讨论的解释)。
4. **§A 的 NaN 组"次日真实超额"数字量级失真,不要直接引用**:train/valid 的 dropped-NaN 组和 added-NaN 组,
   avgN 只有 0.1~2.5(即平均每天不到 1 只甚至只有零点几只),`cell_ann` 的年化换算把个别几天的大波动放大到
   ±1300%~+2000%,这是小样本的数字,不代表任何稳定水平,只有非 NaN 组(avgN>100)的数字是稳的。
5. **`g_tail`(H14 的"只罚最高一档"写法)在配置里跑出来远比 `g_w25` 差**(hl0 Lnet +6.2%/+15.4% 对 +15.1%/+23.7%,
   即使在同一半衰期 hl0 下也差了近 9pp/8pp),而且 `x3_attrib` §B 独立算出"只剔 r≥24.9"只能拿到总增量的 1 成左右
   ——两条路径(配置里的 `g_tail` 表达式,和脚本里的"book3")指向同一个结论:H14 式的单侧剔除写法在这个叠加场景下
   明显弱于用 D30 的完整排序做 0.25 权重叠加,"避开一字板就够"这个简化说法站不住。
6. **`diagnostics.by_year`/`neutralise`/`profile` 只对本次 run 的 stage 内变体生效**,不会像 `rank_corr`
   那样跨阶段读缓存——配置里给 `by_year` 加 `k_mean30` 没有效果。以后要某个老变体的这三类诊断,得把它重新列进
   当次要跑的 stage,否则只能像本轮一样用自写脚本代替。
7. **`mul(cs_rank(...), 浮点常数)` 这种写法在这版引擎上直接合法**,工单给的两级退路((i) `create_like`、
   (ii) 用重复家族项造比例权重)都没用上——如果以后别的因子也要写类似的"排名加权叠加",可以先直接试这种写法。
