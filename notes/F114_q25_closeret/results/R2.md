## 没人要但值得注意的

1. **`study.sh digest` 打印的 `short tr` 列,在 `hlL ≠ hlS` 时和同行的 `Lgross` 不是同一本账本,不能直接拿来套公式还原 `long_share`。** JSON 里每个变体有两本独立的书:`books.by_rank.long`(用多头口径半衰期 `hlL` 平滑)和 `books.by_rank.ls`(用多空口径半衰期 `hlS` 平滑),各自都有自己的 `short_gross_ann` 字段。`digest` 工具打印的主表里,左边一组列(`Lnet`/`Lshp`/`Lgross`/`LTO`)全部来自 `long` 账本,右边一组列(`LS`/`short tr`)全部来自 `ls` 账本——`hlL=hlS` 时两本账本碰巧一样,数字对不上的问题就不会出现;`hlL≠hlS` 时会不一样。本工单里 `s3_w30`(hlL20/hlS10)、`s3_w60`(hlL3/hlS5)、`s4_mean60`(hlL10/hlS5)、`h12_res_best_m30`(hlL10/hlS20)、`h12_sub_best_m30`(hlL2/hlS1)都撞上了这个情况(相差 1~4pp,例如 `s3_w60` 的 `short tr`:同账本 `10.6%` vs `digest` 直接打印的 `11.5%`)。本结果卡全部表格统一取**同一本 `long` 账本**的 `short_gross_ann`(验证过:`Lgross_long/(Lgross_long+short_long)` 在全部 13 个变体上都精确等于 JSON 存的 `long_share`,不多不少),并把 `long_share` 直接列出来,免得再出现换算误差。**这不是只有 `short tr` 一处**:`diagnostics.neutralise` 表里的 `TO` 字段(`_traded_signal`/`all_controls` 等子项下的 `ls_turnover`)也是 `ls` 账本的,和主表的 `LTO tr`(`long_turnover`)不是同一个数,本卡「12. H12 判读专用小表」下面已经单独提过一次,这里不是穷举,只是提醒同一类账本差异可能在别的字段上也存在,往后取数时两本账本要分清楚再比。**附带发现**:`notes/F114_q25_closeret/results/R1.md` 第 (1) 节主表里 `s3_w30`(14.7%)、`s3_w60`(11.5%)两行的 `short tr` 用的是 `ls` 账本读数(与 `digest` 直接打印的一致),按上面这条规则属于"另一种口径",不算读错,只是和本卡的取法不是同一本账本——是否要回去改 `R1.md` 不是我能决定的,放在这里给主研看。

2. **已知家族基准的历史记录(`06_baseline.md`)与现在重读的数字不一致,疑似是旧的 `rank_by` 残留。** `06_baseline.md` 记的 `known_amt_max9`(hl=1,Lnet +8.5%/+20.8%)、`known_stdamt_max9`(hl=0,+9.3%/+18.5%)、`known_ivol_max9`(hl=10,−2.8%/+3.9%),与本次直接读 `S0_baseline.json` 的 `diagnostics.controls` 块算出来的(hl_long=5/5/20,+10.6%/+21.8%、+13.7%/+22.2%、−2.8%/+5.3%)不一样。两次读数的 `rank_ic` 完全相同(+0.0415/+0.0484/+0.0501),只有半衰期选择(进而下游的 Lnet/Lshp)不同;`06_baseline.md` 记的 hl 正好等于当前 JSON 里的 `hl_ls` 字段(1/0/10)。对照 R0 日志已经记过的异常(a)(`S0_baseline.json` 顶层 `rank_by="ls"` 与配置 `rank_by: long` 不一致),本结果卡重新确认过当前 JSON 顶层 `rank_by` 已经是 `"long"`,且这次把 `known_stdamt_mean30` 当普通变体独立重跑(`f_fam_m30`)得到的数字和"现在"这套读数(而不是 `06_baseline.md` 那套)完全吻合。怀疑 `06_baseline.md` 是在顶层 `rank_by="ls"` 期间写的,现在的读数更自洽,但这是读数口径问题不是重算错误,要不要回去改 `06_baseline.md` 留给主研判断。

3. **`s4_w241` 逐年 `long_share` 在 2019/2020 是 −91.0%/−24.9%,机制和 R1 的"分母接近零"不同。** R1 的 `s1_loc` 异常是分母(`long_gross+short_gross`)接近零导致比值被放大;这次 `s4_w241` 的分母并不小(2019 年 `+3.2%`、2020 年 `+7.9%`),是**分子**(`long_gross_ann`)本身变成负的(−2.9%/−2.0%)——即 241 日窗口版在这两年里,按多头十分位选出来的那组股票,原始(未扣基准)的组合收益本身就跑输了。

4. **`cs_regres` 取交集没有把覆盖率打下去**,工单「兜底」一节提到的担心(`cs_regres`/`cs_rank` 组合可能掉覆盖率)没有发生:三条残差变体(`h12_res_base_m30`/`h12_res_best_m30`/`h12_res_base_x9`)的 `coverage_labelled` 在 train/valid 都还是 `0.9992`/`0.9995`,和非残差变体完全一样。JSON 里另有一个 `coverage`(不带 `_labelled`)字段,train/valid 分别约 `0.69`/`0.89`,但这个字段在非残差变体(例如 `s3_w60`)上也是同一个数字,说明它是和"有没有标签的总体覆盖"相关的量,不是 `cov` 门槛用的字段,没有被 `cs_regres` 拉低,也不该被当成门槛读。

5. **`h12_sub_best_m30` 是全部 18 个新变体(两次运行合计)里唯一 `sign=+1` 的**,工单已经预判了这个分支("同向组合是 add 还是 sub,事前不知道"),不算意外,但列出来提醒:主表第 11 项已经加粗标出。

6. **`h12_add_best_m30` 的 train `dist`(0.7982)、`h12_sub_best_m30` 的(0.8637)比它们各自的组成部分(`f_fam_m30` 1.0000、`h12_res_best_m30`/原式类的都是 1.0000 或 0.6xxx)低**——两个 rank 相加之后离散度反而下降,没有跌破 0.5 门槛,只是现象,未深究原因。
