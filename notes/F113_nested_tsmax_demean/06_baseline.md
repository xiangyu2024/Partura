## 1. 复现:四个可核对的公布字段全部一致,**但"long" 列对的是毛超额不是净超额**

`batches/B01_single_factors.yaml` 公布的这一行:`sign -1, hl 1, ls(utrain,holdout) [2.54, 1.09], long(utrain,holdout) [0.037, 0.024]`。

| 字段 | 公布值 | S0_baseline(用户口径 utrain) | 一致? |
|---|---|---|---|
| sign | -1 | -1 | 一致 |
| hl | 1 | hlL=1, hlS=1(两种口径都选到 1,见第 2 节) | 一致 |
| ls[0](utrain) | 2.54 | LS utr = **+2.54** | 一致 |
| long[0](utrain) | 0.037 | **Lgross** utr = +3.7%(〔JSON〕`long_gross_ann` = 0.036851);**Lnet** utr 只有 +0.7%(〔JSON〕`long_ann` = 0.006770) | 与 **Lgross** 一致,与 Lnet 不一致 |
| ls[1] / long[1](holdout) | 1.09 / 0.024 | 未读(留出段未读) | 未核对 |

`batches/B01_single_factors.yaml` 文件头注释写的是"扣费多空夏普……/ 多头腿年化超额……",**只对多空夏普写了"扣费",
对多头腿年化超额没有写**;S0_baseline 的数字证实了这一点——`long` 列读到的是多头腿**毛**超额(未扣 15bp 成本),
不是净超额。`study_playbook.md` §6.8 专门提过"把毛超额当成净超额"是审查反复抓到的错误,这里反过来提醒:
**公布表本身的"long"列就是毛超额**,后面写报告引用这条因子的"long: [0.037, 0.024]"时不要当成净超额转述。

## 10. 配置里的 `known_stdamt_mean30` 没有出现在任何已算结果里——时间问题,不是求值失败

`configs/F113_nested_tsmax_demean.yaml` 的 `gates`/`corr_with` 都列了 `known_stdamt_mean30: cross_mean(day_std(Amt), 30)`,
但 `S0_baseline.json` 的 `diagnostics.controls`、`diagnostics.rank_corr_train` 里都没有这一项,`overview_for.py`
的"已知家族"一行也没有。核对了文件时间和 git 历史:`configs/F113_nested_tsmax_demean.yaml` 的 mtime(10-04 11:44)
晚于 `S0_baseline.json` 的 mtime(10-03 17:52);`git log -p` 显示把 `known_stdamt_mean30` 加进这条因子配置的
正是 commit `5ed9d09`(10-04 12:02,比 S0 的 run 晚将近一天)。**结论:S0_baseline 是在这条配置项被加入之前跑的,
不是算子求值失败**。如果要看这条因子和 `known_stdamt_mean30`(B01 第一组里纯多头最好的两个已知家族基准之一)
的中性化 / rank 相关,需要重跑 S0(本研究本次没有重跑,留给下一步决定)。

## 14. 口径对照备忘

`split_dates`〔JSON〕:train `20180102–20211231`(973 个交易日)、valid `20220104–20230807`(386 个交易日,
